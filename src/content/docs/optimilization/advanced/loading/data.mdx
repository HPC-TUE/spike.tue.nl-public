## Data loading

This tutorial assumes that you can configure a ***torch.utils.data.Dataset*** and ***torch.utils.data.DataLoader*** object which efficiently loads data from a local ephemeral PVC mount.
In what follows, we briefly illustrate an overview of the ***torch.utils.data.Dataset*** and ***torch.utils.data.DataLoader*** objects:

```
import os
import pandas as pd
import torch.nn.functional as F
from torchvision.transforms import v2
from torchvision.io import decode_image
from torch.utils.data import DataLoader

class CustomImageDataset(Dataset):
    
	def __init__(self, annotations_file, img_dir, transform=None, label_transform=None):
        
		# Two-columns: string <FILENAME>.<EXT>, int label
		self.img_labels = pd.read_csv(annotations_file)
        
		self.img_dir = img_dir
        
		# Callable types returning torch.Tensor
		self.transform = transform
        self.label_transform = label_transform

    def __len__(self):
        return len(self.img_labels)

    def __getitem__(self, idx):
        img_path = os.path.join(self.img_dir, self.img_labels.iloc[idx, 0])
        
		image = decode_image(img_path)
        label = self.img_labels.iloc[idx, 1]
        
		if self.transform:
            image = self.transform(image)
        if self.label_transform:
            label = self.label_transform(label)
        
		return image, label

training_data = CustomImageDataset("labels_train.csv", "labels_train/", v2.compose([..., ...]), F.one_hot)
test_data = CustomImageDataset("labels_test.csv", "labels_test/", v2.compose([..., ...]), F.one_hot)

train_dataloader = DataLoader(training_data, batch_size=64, shuffle=True, drop_last=True, prefetch_factor=24, num_workers=12)
test_dataloader = DataLoader(test_data, batch_size=64, shuffle=True, drop_last=True, prefetch_factor=24, num_workers=12)

train_batch = next(iter(train_dataloader))
test_batch = next(iter(test_dataloader))
```

## Network latency from a persistent PVC mount at the DDN storage server dominates over computational complexity

Cluster-based supercomputers, a group of supercomputers Spike-1 belongs to, typically do not store bulk of the data which should persist across experiment runs on a computer-local storage solution.
Computer-local storage is used as an intermediate storage solution for the storage of classic temporary files and files accessed frequently throughout the duration of the experiment being ran.
When the experiment finishes, and the workload is officially terminated at the DGX node, the computer-local storage is wiped.
Bulk of the data resides, and persists, at a (flavor of a) separate distributed RAID server accessible using normal directory indexing commands.
The directory indexing commands trigger an underlying software stub system which facilitates what needs to happen across the network for the directory indexing command to be executed properly.
Additionally, you may decide to stream portions of a larger dataset available through a cloud solution from the external cloud location onto computer-local storage directly.

When the ***torch.utils.data.DataLoader*** randomly tries to execute frequent disk accesses across the network using the software stub system, the data loading process will incur significant time overhead.
For every frequent disk access, the stub software is accessed, causing the time overhead.
Just as pre-fetching time is overlapped with GPU training time, network access can be overlapped with pre-fetching time.
In pipelining, we typically refer to this as the introduction of an additional pipelining step.

Additional pipelining steps can be introduced with help of the [SPDL, Scalable and Performant Data Loading](https://facebookresearch.github.io/spdl/main/) package.
For this explanation, we assume that the dataset is pre-sampled already according to a desired sampling pattern.
For example, when stratified random sampling is sufficient, you stratify a dataset according to task labels, and subsequently shard proportionally according to the strata, the dataset.
For example, when requiring domain leave-out sampling, you also shard according to strata, however, this time proportionally based on domain strata.
It is important to remember that network access introduces a limitation on the first sampling procedure in that shards should be proportional according to the type of sampling you would employ locally.
Sampling bias is not introduced because the different pipeline steps can be given the same pseudo-random seed.
This means that when the seed changes, the order by which shards and random access into the shards happens changes accordingly.

```
def download_shard(index: int):
	
	async with aiohttp.ClientSession() as session:
	
		url = f"https://host/images-{index}.zip"
		async with session.get(url) as response:
		
			if resp.status == 200:
			
				path = f"/eph-store/images-{index}.zip"
				f = await aiofiles.open(path, mode='wb')
				await f.write(await response.read())
				await f.close()
				return path

			else:
				return ""

# The standard rank 0, world size 1 configuration assumes 1-1 RAID SERVER node connection
source_1 = spdl.source.utils.embed_shuffle(

pipeline_config = PipelineConfig(
    src=Merge([backend_1.get_config(), backend_2.get_config()], op=sample_shard),
    pipes=[],
    sink=SinkConfig(20)
```

## Interconnect transfer latency from CPU to GPU dominates over computational complexity

Let's assume that I have image data which resides at a local ephemeral PVC mount but it has extremely large dimensions.
This is a situation you typically encounter with medical images such as CT scan, MRI scan, and Histopathology images.
For the machine learning task, these images cannot be compressed because compression introduces unwanted artifact effects (e.g. a fracture prediction based on an unsharp tissue region).
Because the B200 GPUs present in the DGX nodes can computationally process matrices very fast, the transfer latency of the image from CPU RAM to GPU vRAM becomes a major bottleneck.
As a solution to this problem, Nvidia recently introduced the [cuFile API](https://docs.nvidia.com/gpudirect-storage/getting-started/index.html).
The API, by means of a GPU device pointer and the cuFuleWrite method, transfers data from the local ephemeral PVC mount directly into vRAM memory.
There is no intermediate transfer step anymore from the local PVC mount to RAM.

PyTorch provides the ***torch.cuda.gds.GdsFile*** class to interface with the cuFile API, however, the implemented transfer mechanics are rather primitive (transference of bytes with a particular offset).
Therefore, we recommend utilization of higher-level abstractions such as the ***monai.data.dataset.GDSDataset*** class which automatically encodes interaction into the more primitive form of transfer mechanic described earlier.
The package [MONAI](https://github.com/project-monai/monai) has the ability to recognize PyTorch as a tensor computation backend.

