Over the last years, machine learning model pipeline size, due to rapid parameter expansion, has been expanding at a large growth rate.
This rate is typically facilitated by a less stringent inductive bias present in attention-based mechanisms.
Together with increasing dataset sizes, the less stringent inductive bias allows model pipelines to generalize better to a task it needs to perform.
This shifts the scaling ceiling from parameter fit in the context of dataset size and task to the speed at which parameters can be trained effectively.
The speed is controlled by a set of factors including, but not limited to, 1) available vRAM, 2) accelerator ratio, and 3) peak T(FL)OPS accelerators can provide at a particular timestamp.
These factors, including how processing of parameters and tensor operations at different levels of precision influences these factors, take main stage in this knowledge article.
For the examples in the following subsections, we assume you are familiar with the simple model training example in PLACEHOLDER: OPTIMILIZATION/BEGINNER/SYNCHRONIZATION.
In the example, a dataset/dataloader is responsible for copying MNIST dataset batches to RAM, the Module object and batches are synchronized onto a device by means of the ***Module.to(device)*** and ***Tensor.to(device)*** methods, and module parameters are trained.

## Configuration of different graph operators at varying precisions

Historically, machine learning model pipeline parameter training was exclusively performed with the 32-bit floating-point datatype.
The choice for this datatype is controlled by the resolution range that this data type provides, and how well it connects to the typical resolution range a parameter optimization process converges at.
Additionally, the chosen resolution should not cause gradients to vanish beyond the resolution range, resulting in gradients clipped at 0.
One of the earliest accounts of altering the precision of graph operators involves [training at 16-bit floating-point precision](https://arxiv.org/abs/1710.03740), loss/parameter scaling, and updating/storing a master copy of parameters at 32-bit floating-point precision.
This reduces computational complexity because the peak T(FL)OPS at which operations involved in particular layers are processed at increases from FP32 to FP16 TFLOPS.
Additionally, vRAM storage requirements for local layer weights and intermediate layer representations is effectively halved.
This storage requirement is negatively influenced by the requirement for storing a master weight copy at FP32 datatype level.
Training at 16-bit floating-point precision can be configured in PyTorch with help of the ***torch.amp*** package.
The supported PyTorch operations are covered [here](https://docs.pytorch.org/docs/2.13/amp.html#cuda-ops-that-can-autocast-to-float16) and include: gemm, convolution, and recurrent cells (including lstm, gru).
The following example illustrates how ***torch.amp*** can be configured in the ***train()*** method from the earlier referenced example to force lower precision for every supported operation:

In the meantime, newer forms of mixed-precision training have been introduced which lower the layer's considered datatype to 8-bit or 4-bit floating-point.
[8-bit floating-point mixed-precision](https://arxiv.org/abs/2209.05433) in PyTorch is currently [only supported](https://docs.pytorch.org/ao/stable/workflows/training.html#quantized-training) for the ***nn.Linear*** module and ***torch.grouped_mm*** op.
It can be configured with help of the ***TorchAO*** Python package.
[4-bit floating-point mixed-precision](https://arxiv.org/abs/2509.25149) gemm can be configured with help of the Nvidia ***TransformerEngine*** package.
An example of a gemm op recipe can be found [here](https://github.com/NVIDIA/TransformerEngine/blob/main/tests/pytorch/nvfp4/test_nvfp4_gemm_exact.py).
PyTorch can be configured as a computation backend when using the ***TransformerEngine*** package.

## 64-bit floating-point emulation in dgemm and zgemm kernels

Utilizing 4-bit floating-point precision at different linear graph operators in a transformer-style machine learning pipeline is becoming more and more popular.
This has lead to drastic changes in the accelerator ratios Nvidia incorporates in new hardware architectures.
The support for the high-precision 64-bit floating-point accelerator is gradually being phased out.
This is illustrated by the recent change in the [ratio](https://doi.org/10.1177/10943420241313064) of supported 64-bit and 32-bit floating-point tensor core accelerators between the Hopper and Blackwell architectures: 7.4 vs. 27.5.
The ratio is expected to increase in future Nvidia hardware architectures leading to significant 64-bit floating-point accelerator contention when kernels are executed on a GPU.
This is problematic for traditional high-performance simulation applications or physics-based calculations involved in the machine learning pipeline which rely on 64-bit floating-point precision.
The need for this precision stems from correct representation of high-resolution constants (e.g. speed of light) or involved operations which are sensitive to small floating-point changes.

In response, alongside the 64-bit floating-point accelerator gradually being phased out, Nvidia has increased the effort in providing better support for 64-bit floating-point emulation.
The idea of emulation is that with appropriate exponent alignment and mantissa split operations, the gemm operations can be [offloaded](https://doi.org/10.1177/10943420241239588) to 8-bit integer accelerators.
After the gemm operation has been performed, the 64-bit floating-point accelerator is only used for a sum reduction operation back into 64-bit floating-point resolution.
A sum reduction operation generally involves much less FLOPS in comparison to a gemm operation and the large count of 8-bit integer accelerators on the B200 GPU makes time complexity as a result of accelerator contention of the gemm TOPS negligible.

Support for 64-bit floating-point emulation has been added since cuBLAS 13.0.2 for the [dense gemm operators](https://github.com/NVIDIA/CUDALibrarySamples/tree/master/cuBLAS/Emulation) dgemm (64-bit float) and zgemm (128-bit complex).
Support for batched gemm, sparse gemm, and [triangular solving](https://github.com/RIKEN-RCCS/GEMMul8), and better acceleration support for [large matrix sizes](https://doi.org/10.1177/10943420261467787) is expected to arrive in the near future.
