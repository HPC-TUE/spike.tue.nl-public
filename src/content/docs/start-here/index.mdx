Spike is not a self-service cluster where an account is created immediately
after a form is submitted. Access starts with a conversation. The
Supercomputing Center (SCC) first looks at the project, the workload, and the
available capacity. If Spike is the right platform and space is available, an
AI engineer will onboard you personally.

## The route onto Spike

1. **Submit an access request.** Use the
   [Service Desk form](https://tue.topdesk.net/tas/public/ssp/content/serviceflow?unid=93e8b8b00471499593597171aaddaf34)
   as the first step. If your department already tracks the proposal in the
   Research Cockpit, include that reference in the request instead of creating
   an unrelated second record. Describe the research question, the expected GPU
   workload, your data, and the period in which you need the system.
2. **Discuss the project with an SCC AI engineer.** During the intake, you will
   look at eligibility, technical fit, data handling, expected scale, and
   whether Spike offers a real advantage over another computing platform.
3. **Receive a capacity decision.** If the project is a good fit and the cluster
   has room, onboarding can be scheduled. If the cluster is full, SCC will put
   the project on the waiting list rather than promise capacity that is not
   available.
4. **Onboard together.** Set aside part of a day with an AI engineer. You will
   learn the Spike-specific workflow, including projects, containers, loading
   data, storage, submitting work, and checking a running workload.
5. **Start with an engineer nearby.** After onboarding, you will remain in close
   contact with an SCC AI engineer while you bring up the first real workloads,
   resolve early problems, and learn to use the system efficiently.

## Come prepared

The onboarding session teaches you how to work on Spike; it is not an
introduction to machine learning, Linux, Python, or your research software.
Before applying, have:

1. **Code that is close to runnable on HPC.** It does not need to be packaged
   perfectly for Spike yet, but it should not still require weeks of development
   before a meaningful test can run. SCC understands that moving into containers
   and onto B200 GPUs takes some adjustment.
2. **An estimate of the dataset size.** The data should be ready to transfer, and
   you should know roughly how much needs to move onto the platform.
3. **A project name.** Use one name consistently in the access request and during
   onboarding.
4. **A list of users.** Identify everyone who will need access to the project.
5. **An understanding of data sensitivity.** Know the expected classification
   and discuss any uncertainty with your data steward before data is transferred.

You should also understand your own code and be comfortable working from a
terminal. Container experience is helpful, but SCC can help translate an
otherwise working environment into the Spike workflow.

The [Access and intake](/start-here/intake/) guide explains what makes a strong
request, how SCC assesses fit, and what to prepare for the intake and onboarding
sessions.
