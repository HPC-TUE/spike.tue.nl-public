The guides in this section cover workflows that need more coordination than a
standard single-GPU training run. They assume that your image, command, data
mounts, checkpoints, and first training result already work on the smallest
approved compute resource.

:::caution
Do not change a compute-resource preset, GPU count, worker count, priority, or
preemptibility without permission from your SCC AI Engineer. Multi-GPU and
multi-node runs can reserve a substantial part of the cluster and must be
planned with them.
:::

## Before you scale

You should be able to answer all of the following:

1. Does the same immutable image and command complete on one GPU?
2. Are the dataset, outputs, and checkpoints on approved persistent storage?
3. Can the application restart from a checkpoint without silently repeating or
   skipping data?
4. Have you recorded the image tag, code revision, dataset version, random
   seed, and baseline result?
5. Does your SCC AI Engineer know the intended GPU count, worker count, runtime,
   and expected benefit?
6. Can you save diagnostic output promptly? Run:ai workload logs disappear
   shortly after a workload stops or fails.

## What Run:ai manages—and what your code must manage

Run:ai schedules pods, applies project policy, attaches data sources, and
allocates the approved compute resource. Your application still has to start
the correct number of processes, assign one process to each GPU, coordinate
ranks, aggregate metrics once, and write recoverable checkpoints.

For platform concepts, use NVIDIA's current [Run:ai workload
documentation](https://run-ai-docs.nvidia.com/saas/workloads-in-nvidia-run-ai/workloads).
For framework behavior, use the official [PyTorch distributed
overview](https://docs.pytorch.org/tutorials/distributed.html) or [Hugging Face
Accelerate documentation](https://huggingface.co/docs/accelerate/index).
