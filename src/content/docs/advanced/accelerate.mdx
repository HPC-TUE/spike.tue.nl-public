[Hugging Face Accelerate](https://huggingface.co/docs/accelerate/index) adapts a
PyTorch training loop to different device layouts and launches the required
processes. Run:ai still schedules the pod or pods, mounts data, and allocates
the approved GPUs; Accelerate does not request cluster resources by itself.

## Adapt the training code

At minimum, create one `Accelerator`, prepare the model, optimizer, dataloader,
and scheduler, and use `accelerator.backward(loss)`. The official [Accelerate
quick tour](https://huggingface.co/docs/accelerate/quicktour) shows the complete
code changes.

Keep rank-sensitive work behind the Accelerate helpers:

```python
from accelerate import Accelerator

accelerator = Accelerator()

model, optimizer, train_loader = accelerator.prepare(
    model, optimizer, train_loader
)

for batch in train_loader:
    optimizer.zero_grad()
    loss = model(**batch).loss
    accelerator.backward(loss)
    optimizer.step()

accelerator.wait_for_everyone()
if accelerator.is_main_process:
    save_final_metadata()
```

The checkpoint must include enough state to resume the experiment, including
the model, optimizer, scheduler, current step or epoch, and random state where
the application depends on it.

## Pin the Accelerate configuration

Generate a configuration with `accelerate config`, review it, and store the
result with the code. A single-node, four-GPU configuration has this general
shape:

```yaml
compute_environment: LOCAL_MACHINE
distributed_type: MULTI_GPU
machine_rank: 0
main_process_ip: null
main_process_port: null
mixed_precision: bf16
num_machines: 1
num_processes: 4
use_cpu: false
```

The `num_processes` value must match the GPUs allocated to the pod. Do not copy
`bf16`, the process count, or any FSDP option without validating that it matches
the model, image, and approved compute resource.

## Configure the Run:ai workload

1. Build an immutable image containing the training code, Accelerate version,
   configuration file, and dependencies.
2. Create or select a Run:ai environment for that image.
3. Under **Runtime settings**, set the tested command explicitly:

   ```bash
   accelerate launch \
     --config_file /workspace/config/accelerate.yaml \
     /workspace/train.py \
     --epochs 1
   ```

4. Select the approved compute-resource preset whose GPU count matches
   `num_processes`.
5. Mount persistent data and checkpoint paths.
6. Run a short test and verify that only the main process writes shared output.

## Progress to FSDP

FSDP is useful when a model or optimizer state does not fit comfortably on one
GPU. It adds sharding, wrapping, mixed-precision, and checkpoint decisions that
must be tested together.

1. Keep the same single-GPU baseline and expected result.
2. Add an FSDP configuration generated for the installed Accelerate version.
3. Validate a short single-node multi-GPU run.
4. Save and reload a sharded checkpoint.
5. Compare convergence and effective global batch size with the baseline.
6. Attempt multi-node only after review with your SCC AI Engineer.

Use the official [Accelerate FSDP
guide](https://huggingface.co/docs/accelerate/usage_guides/fsdp) and PyTorch
[Distributed Checkpoint
guide](https://docs.pytorch.org/tutorials/recipes/distributed_checkpoint_recipe.html)
for current configuration and checkpoint APIs.

:::caution
Changing `num_processes` or `num_machines` does not allocate more hardware.
Run:ai resources and the Accelerate topology must agree. Do not change GPU,
worker, priority, or preemptibility settings without SCC AI Engineer approval.
:::

For multi-node work, follow [Multi-GPU and multi-node
training](/advanced/multi-gpu/). The launcher must run on every participating
pod with coordinated ranks and rendezvous settings; a single-node Accelerate
configuration is not sufficient.
