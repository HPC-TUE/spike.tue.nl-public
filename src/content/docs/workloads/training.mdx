Use a **training** workload for non-interactive work that should have a clear
command, logs, and completion state. Use an interactive workspace only when you
need a shell or notebook session, and use an inference workload for a serving
endpoint.

## First training run

1. In Run:ai, select the correct project and choose **New workload** → **Training**.
2. Give the workload a descriptive, non-sensitive name.
3. Select the environment or image tag you published in Harbor.
4. Select the smallest approved compute-resource preset that can run the test.
5. Attach the required data source or persistent volume. Use ephemeral storage only for disposable data.
6. Enter a command that produces a visible result, submit it, then open the workload details.
7. Follow the logs until the workload reaches **Running** and then **Completed**.

## Shared memory for data loaders

Linux containers normally have a small `/dev/shm` shared-memory filesystem.
Multiprocessing data loaders, browser processes, and distributed communication
libraries can exhaust it even when normal CPU and GPU memory are still
available. Typical symptoms include a data-loader worker exiting unexpectedly,
`Bus error`, or `No space left on device` for `/dev/shm`.

Check the current allocation inside a small running workload:

```bash
df -h /dev/shm
```

If the workload needs more shared memory, discuss the required size and reason
with your SCC AI Engineer. They can approve a compute resource with **Increase
shared memory size** enabled. NVIDIA documents this setting in the Run:ai
[compute-resource guide](https://run-ai-docs.nvidia.com/saas/workloads-in-nvidia-run-ai/assets/compute-resources).
Do not change the compute-resource preset yourself.

Some workloads instead need an engineer-approved ephemeral volume mounted at
`/dev/shm`. In that case, use only the storage class, size, and persistence
choice provided by the engineer. The volume is disposable and may use storage
rather than RAM; it is not a location for checkpoints or the only copy of
results.

After the change, rerun the smallest test, check `df -h /dev/shm`, and confirm
that data-loader workers start and stop cleanly. Increasing shared memory does
not fix an application that leaks workers or creates more processes than the
approved CPU allocation can sustain.

## GPU quota, priority, and retries

Start with one GPU. Request a fractional GPU only where the selected
compute-resource preset explicitly supports it. Multi-GPU and distributed
training require an application launcher and architecture that match the
selected resources; test the single-GPU path first.

### The default scheduling state

All projects use the same scheduling weight. By default, all projects run in
the over-quota state, so an ordinary GPU request does not receive a higher place
in the queue simply because it belongs to a particular project. Over quota
means that the project may use available capacity under the default policy; it
is not a promise that GPUs are immediately available.

### Requesting a scale-up

When a project is ready for a larger run, request a temporary quota and priority
change from the Spike administrators. Include:

1. The project and workload owner.
2. The GPU type, count, and compute-resource preset required.
3. Why the scale-up is ready now (for example, the one-GPU run is validated).
4. The requested start date and number of weeks for the scale-up.
5. Expected utilization, checkpointing, and a contact for the work.

The administrators decide whether to grant the additional quota. If approved,
they grant the project GPU priority for the agreed number of weeks. This is a
temporary scheduling window for the scale-up, not a permanent change to the
project's allocation.

### When the priority window ends

At the end of the agreed period, the administrators scale the project back to
its normal over-quota state. Plan checkpoints, evaluation, and cleanup before
the window expires; do not assume that the temporary priority will continue.

Priority does not remove workload limits or make an unsuitable request
schedulable. The selected resource, available GPU type, workload state,
preemptibility, and project policy still apply. A preemptible workload must
persist checkpoints and tolerate being retried. Cancel stale test workloads and
delete completed disposable workloads to keep project resources understandable.

:::note
For a first test, use the smallest approved resource and wait under the default
over-quota policy. Ask for a scale-up only after the workload is reproducible
and you can describe the required GPU window.
:::

:::note
If a workload remains pending, inspect its selected project, image, resources,
and data sources before changing settings. The [troubleshooting guide](/troubleshooting/)
lists safe checks and escalation details; it also explains what to include when
requesting a quota or priority review.
:::
